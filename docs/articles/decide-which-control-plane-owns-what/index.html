Decide which agent control plane is authoritative for what

CIO
CTO
AI control plane
Most enterprises will run more than one agent control plane. A default split says which one holds the record for inventory, identity, policy and audit.
Published

October 22, 2026

Last checked

October 22, 2026

Reading time

4 min

Most enterprises that build agents on more than one platform will run more than one agent control plane. Microsoft describes Agent 365 as “the control-plane for AI agents,” with Microsoft Entra Agent ID for agent identities.1 The other large platforms each offer a plane of their own, and each one governs its own estate well. Once agents from different estates start to share data and processes, someone has to decide which plane is authoritative for which job.

Each native plane governs its own estate

The native planes cover similar ground, each inside its own walls. Amazon Bedrock AgentCore’s services include a runtime, memory, a gateway that connects MCP servers, identity and OpenTelemetry-compatible observability.2 Google’s Gemini Enterprise Agent Platform includes an agent registry, an agent gateway and agent identities.3 Agentforce is a platform for building, running and optimizing agents inside Salesforce, with trusted context and controlled behavior.4

Their claims also overlap. Microsoft’s guidance for its own estate names Agent 365, or Entra Agent ID where Agent 365 is not in use at scale, as the authoritative inventory, and it asks for consistent policy across every agent platform.5 An enterprise with two or three such planes has two or three candidates for the record of its agents, and it has to settle which record counts before an audit raises the question for it.

Where each plane is authoritative

The handbook’s default keeps each native plane authoritative for identity and runtime inside its own estate. A vendor-neutral plane, which the handbook realizes with MuleSoft Agent Fabric, is then authoritative for the cross-estate inventory, for policy on every call into enterprise capabilities and data, for orchestration across vendors, and for cost and audit.4

The split holds only when the planes share what they know. Each agent’s identity should be federated from the plane that issued it, so every plane checks the same identity. One registry has to hold the record of ownership, or an agent that appears in two inventories ends up with two owners or none. Every plane’s telemetry also belongs in one trace, so that an action that starts in one estate and finishes in another can be followed end to end.

The native planes keep running and securing the agents inside their own estates. The vendor-neutral plane governs the crossings, where an agent’s work reaches another estate or the enterprise’s own systems and data.

What to do next

  1. CIO. List every agent platform in use, and for each one record which system is authoritative for inventory, identity, policy and telemetry, with a named owner for each decision.
  2. CTO. Federate agent identities from the plane that issued them, and send every agent’s calls into enterprise APIs, tools and data through one policy point, whichever estate the agent runs in.
  3. CIO and CTO. Agree which registry holds the record of ownership, and send telemetry from every plane to one trace before the next agent platform goes live.
