Keep the agent roster and its risk rule in configuration

CTO
AI Engineer
Architect
AI
When agents and approval rules live in code, every change is a release. Move them into one reviewed file, and the same graph runs another business.
Published

November 8, 2026

Last checked

November 8, 2026

Reading time

4 min

In most agent frameworks the roster is written in code, with a class for each agent, a router with a branch for each destination and edges wired by hand.1 That holds until the business wants a new specialist or a stricter approval rule, and then each request becomes a software release.

What belongs in the file

The config-driven agent network in this site’s Guides & Labs keeps four things in one XML file: the prompt its broker routes with, the prompt it uses to write an answer and score that answer’s risk, the scenarios, and the agents.2 The graph is built when the file loads, with a node for every agent the file declares, so a new agent is a new XML block and a new business is a new file.1,3

Here is one agent from the travel network’s file, shortened to two of its five scenario replies.

<agent id="revenue_strategist" name="Revenue Strategist">
  <description>pricing, rates</description>
  <mock_data default="Rates are optimal.">
    <response scenario_id="1">{"your_rate": 250, "comp_rate": 200, "variance": "Drop rate by $50", "recommendation": "Drop Rate"}</response>
    <response scenario_id="5">{"alert": "Price War", "comp_move": "-$30 drop", "recommendation": "Match competitor rate or add value"}</response>
  </mock_data>
</agent>

The description is all the broker sees when it decides whom to consult, so those three words carry real weight.2 Each response is a reply written in advance, because the network is a prototype. Its routing, synthesis and human gate run against gpt-4o, while no vendor API is called and nothing is fetched.1 A second file turns the same graph into a management consulting firm, with five different specialists, a different routing prompt and a different risk rule, and the two networks differ by no lines of Python.2

Review the file the way you review policy

Moving the roster out of code doesn’t make it harmless, because the file decides who is consulted and when a person is interrupted. In the travel network, any recommendation to change prices or publish content stops at the human gate. In the consulting network the gate stops layoffs, major restructuring and budget moves over $1M.2 Editing that one sentence changes what a model may do without a person’s approval, the kind of change an architecture review would normally see.

The rule is also prose. The model is asked to score its own recommendation, and the gate opens only when its answer contains the words “RISK: YES”, so the rule is only as reliable as the model’s reading of it.2,3 The code holds what should not depend on a prompt. The loader refuses a file that lacks a required element or declares no agents.4 The router’s choices are checked against the roster, and every fallback is logged.3 An approved proposal goes back to the user word for word, because generating it a second time could hand them something other than what they approved.1

That split is a useful test for any agent platform. Configuration should say which agents this business has and when to ask a person, and code should enforce what must hold in every business.

What to do next

  1. CTO. Ask each agent platform you evaluate where its roster, routing prompts and approval rules are defined, and whether changing one needs a release.
  2. Architect. Keep agent configuration under version control with a named reviewer, and give a change to an approval rule the same sign-off as any other policy change.
  3. AI Engineer. Keep validation, logged fallbacks and the approval path in code, and test the real graph against a stub model, as the network’s 19 checks do with no API key.2
